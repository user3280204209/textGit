# 直连对话通道（前端聊天页的地基）

> 目标读者：要写前端聊天界面、或第一次接触本项目后端的人。
> 阅读顺序：先看"一"，再看"三"的文件职责表，最后按"四"动手验证。

---

## 一、这条通道长什么样

```
浏览器                              后端                        模型服务
┌────────────────────┐   POST     ┌─────────────────────┐    ┌──────────────────┐
│ useChat.ts         │ ─────────► │ api/chat.py         │ ─► │ POST /chat/      │
│  messages[]        │  {messages}│  校验 → 转发         │    │   completions    │
│   ↑ append（雪球） │ ◄───────── │ core/llm.py         │ ◄─ │                  │
└────────────────────┘  {reply}   └─────────────────────┘    └──────────────────┘
```

一句话：**"滚雪球"这个动作发生在浏览器里，不在后端。**
前端每次把完整历史发过来，后端只负责转发并返回新的一句，自己不存历史。

## 二、和你日常脚本的对照

日常脚本写法：

```python
client = OpenAI(api_key=..., base_url="https://api.deepseek.com/v1")
messages = []
messages.append({"role": "user", "content": q})
resp = client.chat.completions.create(model="deepseek-chat", messages=messages)
messages.append({"role": "assistant", "content": resp.choices[0].message.content})
```

搬到本项目的对应位置：

| 日常脚本里的东西 | 本项目里的位置 | 备注 |
|---|---|---|
| `OpenAI(api_key=..., base_url=...)` | `core/llm.py` 的 `get_async_client()` | Key/地址从 `backend/.env` 读，全项目唯一入口 |
| `messages = []` 这个列表 | 前端 `hooks/useChat.ts` 里的 React state | 雪球搬到了浏览器 |
| `client.chat.completions.create(...)` | `api/chat.py` 里那 4 行 | 只多了一个 `await` |
| `resp.choices[0].message.content` | `api/chat.py` 的 `response.choices[0].message.content` | 原样 |
| `messages.append(...)` | `useChat.ts` 里收到 reply 后的 `setMessages` | 原样 |

**结论：你日常会的那套一个概念都不用丢，只是多了一层 HTTP。**

## 三、文件职责表

### 后端

| 文件 | 职责 | 改动状态 |
|---|---|---|
| `app/core/config.py` | 读 `.env`。Key / base_url / 模型名全在这 | 未改（本来就够用） |
| `app/core/llm.py` | **唯一模型入口**。新增 `get_async_client()` 返回原生 `AsyncOpenAI` | 已改 |
| `app/core/schemas.py` | **契约唯一真相源**。新增 `ChatUsage` / `ChatRequest` / `ChatResponse` | 已改 |
| `app/api/chat.py` | `POST /api/chat`。收历史 → 调模型 → 返回一句 | **新增** |
| `app/api/__init__.py` | 路由注册表，加一行 `include_router` | 已改 |

### 前端（第 2 步才做，此处先列清职责）

| 文件 | 职责 |
|---|---|
| `src/types/api.ts` | 加 `ChatMessage` / `ChatResponse`，**必须与 `schemas.py` 对齐** |
| `src/api/client.ts` | 加 `api.chat(messages)`，网络唯一入口 |
| `src/hooks/useChat.ts` | **核心**：`messages` 状态 + append 雪球 + loading / error |
| `src/components/MessageBubble.tsx` | 一个气泡，区分 user / assistant |
| `src/components/ChatInput.tsx` | 输入框，回车发送，发送中禁用 |
| `src/pages/ChatPage.tsx` | 拼装列表 + 输入框 + 自动滚到底 |
| `src/App.tsx` | 首页换成 `ChatPage`，自检页挪到 `/debug` |

### 为什么这么切分

1. **一个文件回答一个能被单独问出来的问题**
   连不上后端看 `client.ts`；消息不刷新看 `useChat.ts`；样式错看 `index.css`。
2. **契约集中在一处**
   `schemas.py` ↔ `types/api.ts` 一一对应，这是 README 第五节第 4 条铁律。
3. **留给"串起来"的插槽**
   以后 `ChatPage` 左侧挂画像侧栏（读 `/api/profile/{id}`），
   聊到学习资源时气泡按 `resource_type` 分发到不同卡片组件。目录一个都不白留。

## 四、怎么验证（不用写前端就能测）

### 4.1 前置：填 Key

编辑 `backend/.env`：

```
LLM_API_KEY=sk-你的真实Key
```

⚠️ 留空时接口会返回 `503 未检测到 LLM_API_KEY`，这是**刻意的防呆**，不是 bug。
留空比填假 Key 好：假 Key 会得到难懂的 SDK 报错。

### 4.2 启动后端

```powershell
$env:PYTHONUTF8 = "1"          # 见第五节坑 1，中文 Windows 必加
cd backend
..\.venv\Scripts\python.exe -m uvicorn app.main:app --reload --port 8000
```

> 端口被占的排查方法见第五节坑 2。

### 4.3 在 `/docs` 里点着测

打开 `http://127.0.0.1:8000/docs` → 展开 `对话` → `POST /api/chat` → Try it out：

```json
{
  "messages": [
    {"role": "user", "content": "你好，用一句话介绍你自己"}
  ]
}
```

**亲手体验"滚雪球"**：拿到 `reply` 后，把它追加进 `messages` 再发一次：

```json
{
  "messages": [
    {"role": "user", "content": "你好，用一句话介绍你自己"},
    {"role": "assistant", "content": "<把上一次的 reply 原样粘进来>"},
    {"role": "user", "content": "那你能帮我学 Python 吗？"}
  ]
}
```

第二次回答能接上第一次的上下文 —— 这就是雪球滚起来了。
第 2 步做前端时，`useChat.ts` 干的就是"自动帮你粘"这件事。

### 4.4 错误路径也要测

| 情况 | 期望 |
|---|---|
| `LLM_API_KEY` 为空 | `503` + 中文提示 |
| `messages` 为 `[]` | `422` 参数校验 |
| Key 填错 | `502` + "API Key 无效，请检查 backend/.env 里的 LLM_API_KEY" |
| 断网 | `502` + "无法连接模型服务 ..." |

## 五、踩坑记录（中文 Windows 特有，组员必看）

### 坑 1：`pip install -r requirements.txt` 报 `UnicodeDecodeError: 'gbk' codec`

**原因**：`requirements.txt` 是 UTF-8，带中文注释；pip 用系统区域编码（中文 Windows = GBK）去读它。

**解决**：装依赖前先开 Python 的 UTF-8 模式：

```powershell
$env:PYTHONUTF8 = "1"
pip install -r backend/requirements.txt
```

**建议**：让 `scripts/setup.ps1` 在调 pip 之前自动设置这个变量，
否则每个中文 Windows 组员都会在第一步卡住。

### 坑 2：`uvicorn` 启动报 `[Errno 13] ... 以一种访问权限不允许的方式做了一个访问套接字的尝试`

**含义**：不是代码问题，是 **8000 端口已被别的软件占用**（Windows 报 WSAEACCES）。

**排查**：

```powershell
netstat -ano -p tcp                    # 找 8000 那行最右边的 PID
Get-Process -Id <PID> | Select ProcessName,Path
```

**本机实际情况（已解决）**：占用者是 **C-Lodop 云打印控件**
（`CLodopPrint32.exe`，注册了自动启动服务 `CLodopPrintService`，常驻 8000 和 18000）。
已于 2026-09-22 通过其自带卸载程序卸掉，8000 端口已释放。

> 如果你换了台机器又碰到同样报错，先按上面两条命令查出占用者，
> 再决定是卸掉它、还是把后端换到别的端口。

**换端口的注意点**：若选择换端口，必须**前后端一起改** ——
后端起在 8010，就要把 `frontend/vite.config.ts` 里 `proxy` 的
`target` 也改成 `http://127.0.0.1:8010`，否则前端会报"无法连接后端"。

### 坑 3：日志里的中文显示成乱码

同样是控制台编码问题。`$env:PYTHONUTF8 = "1"` 一并解决。

### 坑 4：用 PowerShell 调接口，返回的中文全是乱码

**现象**：`Invoke-RestMethod` 拿到的 `reply` 显示成 `å°æ˜Ž` 这种。

**原因**：FastAPI 返回的响应头是 `Content-Type: application/json`，**不带 charset**。
PowerShell 在这种情况下按 Latin-1 解码，而实际字节是 UTF-8。

**这不是服务端 bug**，已实测证明：用 httpx 拿原始 bytes 显式 `.decode("utf-8")`，
得到的是完全正确的中文。**浏览器和 axios 会按 UTF-8 解码，前端不会乱码。**

**验证方法**（想自己确认时用）：

```python
# 在 backend 目录下，用 venv 的 python 跑
import httpx
r = httpx.post("http://127.0.0.1:8000/api/chat",
               json={"messages": [{"role": "user", "content": "回复：学习使我快乐"}]},
               timeout=120)
print(r.content.decode("utf-8"))   # 显式按 UTF-8 解码原始字节
```

**结论**：看到乱码先别改代码，先确认是不是工具的解码问题。

## 六、实测记录（本机跑通的三轮对照）

用真实 DeepSeek Key 跑通的三轮对照，**证明了"雪球由前端滚"这个设计**：

| 轮次 | 发出的 messages | 模型回答 | prompt tokens |
|---|---|---|---|
| 1 | 仅 1 条 user：`我叫小明，我在学 Python 数据分析…` | 「小明，我记住了你在学 Python 数据分析。」 | 23 |
| 2 | **追加了第 1 轮的 reply**，再问「我叫什么？在学什么？」 | 「小明，Python 数据分析。」✅ 记得 | 105 |
| 3 | 只发「我叫什么？在学什么？」（**不带历史**） | 「你叫小明，在学编程。」❌ 纯属瞎猜 | 23 |

第 3 轮是关键对照：**同一个问题，不带历史模型就答错**。
说明上下文完全由前端那个 `messages` 数组携带，后端确实无状态。
第 2 轮 `prompt_tokens` 从 23 涨到 105，也正是"历史被带上了"的量化证据。

## 七、下一步（第 2 步预告）

后端通了之后，前端要做的就三件事：

1. `types/api.ts` 补类型 → `client.ts` 补 `api.chat()`
2. `useChat.ts` 把雪球滚起来（这是全项目最像你日常脚本的一个文件）
3. `ChatPage.tsx` 把消息渲染出来

到时候 `src/` 下会多出 `hooks/` 和 `components/` 两个目录 —— 它们不是凭空来的，
是因为"状态逻辑"和"渲染逻辑"要分开，才自然长出来的。
