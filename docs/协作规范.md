# 协作规范

> 组员多、基础不一，**流程不统一比技术难更致命**。
> 本文是硬性约定，不是建议。

---

## 一、分支模型

我们只用一个长期分支 `main`，其余全是临时功能分支。

```
main ────●────────●────────●────────●──→  （永远可运行）
          \      /          \      /
           ●───●            ●───●
         feature/画像      feature/前端
```

### 规则

| 分支 | 用途 | 谁可以推 |
|---|---|---|
| `main` | 稳定分支，**必须随时能跑起来** | ❌ 任何人不得直接 push |
| `feature/xxx` | 功能开发 | 开发者自己 |
| `fix/xxx` | 修 bug | 开发者自己 |
| `docs/xxx` | 只改文档 | 开发者自己 |

### 命名规范

```
feature/profile-agent        画像智能体
feature/resource-generation  资源生成
feature/frontend-chat        前端对话界面
feature/learning-path        学习路径
fix/profile-json-parse       修复画像 JSON 解析
docs/setup-guide             文档
```

> ❌ 不要用 `test`、`aaa`、`mybranch`、`张三的分支` 这种名字。
> 一周后你自己都不知道那是什么。

### 开新分支

```powershell
git checkout main
git pull                          # 必须！基于最新 main 开分支
git checkout -b feature/你的功能名
```

## 二、提交规范

### 提交信息格式

```
<类型>: <简短描述>
```

| 类型 | 含义 | 例子 |
|---|---|---|
| `feat` | 新功能 | `feat: 完成画像智能体的多维度抽取` |
| `fix` | 修 bug | `fix: 修复无 API Key 时返回 500 而非 503` |
| `docs` | 只改文档 | `docs: 补充 pnpm 安装说明` |
| `refactor` | 重构，不改功能 | `refactor: 抽取 LLM 客户端工厂` |
| `test` | 加测试 | `test: 补充资源类型注册表校验` |
| `chore` | 杂项（依赖、配置） | `chore: 升级 langgraph 到 1.2` |

### 好的提交 vs 坏的提交

✅ 好的：
```
feat: 实现练习题目智能体，支持 4 种题型
fix: 修复画像 JSON 被 markdown 围栏包裹时解析失败
docs: 补充 Windows 下 pip 换源方法
```

❌ 坏的：
```
update          ← 更新了什么？
修改             ← 改了哪里？
111             ← ？
最终版           ← 哪个最终版？
再改一次         ← ……
```

### 提交粒度

**一个提交只做一件事。**

- ✅ 实现画像智能体 → 一个提交
- ✅ 修复画像解析 bug → 另一个提交
- ❌ 实现画像 + 顺手改了前端样式 + 顺便升级了依赖 → 应拆成三个

> 好处：出问题时能精准回滚，code review 也能看懂。

### 提交前必做

```powershell
# 1. 看自己改了什么，确认没有误提交
git status
git diff

# 2. 确认 .env 没有被加进来（关键！）
git status | findstr ".env"
# 如果出现了 .env 而没有 .env.example，立刻停止并检查！

# 3. 跑一遍检查
cd backend
conda activate learnagent
ruff check .
pytest
cd ..\frontend
pnpm lint
pnpm typecheck
```

> ⚠️ **绝对不要 `git add .`**
> 它会把你不想提交的东西（临时文件、误建的 `.env`、生成的资源）全加进去。
> 用 `git add <具体文件名>` 或 `git add backend/app/agents/`。

## 三、Pull Request（合并请求）

### 流程

1. 推自己的分支：
   ```powershell
   git push -u origin feature/你的功能名
   ```

2. 到 GitHub 上开 Pull Request（目标分支选 `main`）

3. **至少 1 人 review 通过后才能合并**

4. 合并后删掉自己的功能分支

### PR 描述模板

```markdown
## 做了什么
（一句话说明）

## 对应需求
需求点 2：多智能体协同的资源生成

## 怎么验证
1. 启动后端
2. 调 POST /api/resources/generate
3. 期望看到 5 类资源全部返回

## 需要 review 的重点
- 画像提示词的抽取准确度
- 并行调度是否有竞态问题
```

### Review 检查清单

reviewer 请重点看：

- [ ] `main` 分支能跑起来吗
- [ ] 有没有把 `.env` 或密钥提交上来
- [ ] 改了 `schemas.py` 的话，`frontend/src/types/api.ts` 同步了吗
- [ ] 新增资源类型的话，在 `RESOURCE_AGENT_REGISTRY` 注册了吗
- [ ] `ruff check` 和 `pytest` 过了吗
- [ ] 有没有硬编码的路径、密钥、模型名

## 四、代码约定

### 后端

| 项 | 约定 |
|---|---|
| 缩进 | 4 空格 |
| 行长 | 100（`ruff` 管的） |
| 命名 | 变量/函数 `snake_case`，类 `PascalCase`，常量 `UPPER_CASE` |
| 类型标注 | **必须写**，FastAPI 靠它生成文档 |
| 注释 | 写**为什么**，不写**是什么** |
| 配置 | 一律走 `app/core/config.py`，禁止 `os.getenv` |
| 网络 | 一律走 `app/core/llm.py`，禁止在 agent 里直接建客户端 |

### 前端

| 项 | 约定 |
|---|---|
| 缩进 | 2 空格 |
| 引号 | 双引号 |
| 命名 | 组件 `PascalCase`，变量 `camelCase`，常量 `UPPER_SNAKE` |
| 网络请求 | **必须走 `src/api/client.ts`**，禁止组件里直接 `fetch`/`axios` |
| 类型 | 禁止 `any`（`strict` 模式会报错） |
| 路径别名 | 用 `@/` 而不是 `../../..` |

### 共同的

- **文件编码 UTF-8，行尾 LF**（`.editorconfig` 已配好，装插件即可生效）
- 不要提交注释掉的大段代码，不要的代码就删掉（Git 里有历史）
- 不要提交 `console.log` / `print` 调试语句
- 中文注释**可以用也要鼓励**，但要写清楚，不要写"这里处理一下"

## 五、需求对齐检查

每次提 PR 前,对照这份表确认你的改动是否影响需求达标：

| 需求 | 硬性指标 | 当前实现位置 |
|---|---|---|
| 1. 对话式画像 | **≥6 个维度**，支持随学随新 | `agents/profile_agent.py` |
| 2. 多智能体架构 | 须体现**协作** | `agents/` + `graph/orchestrator.py` |
| 2. 资源生成 | **≥5 种类型** | `agents/resource_agents.py` |
| 3. 学习路径 | 明确步骤和顺序 | `api/path.py` |
| 3. 精准推送 | 基于画像 | `PathStep.resource_ids` |
| 4. 智能辅导 | 加分项 | **待认领** |
| 5. 效果评估 | 加分项 | **待认领** |

> 如果 `pytest` 里的 `test_every_resource_type_has_agent` 挂了，
> 说明你加了资源类型但没注册智能体 —— **生成时会静默少一项**，必须修。

## 六、分工建议（组员多时）

按**需求模块**切分，而不是按"前端/后端"切分 ——
后者会导致有人没事干、有人忙死。

| 模块 | 人数建议 | 交付物 |
|---|---|---|
| 画像构建 | 2 | 画像抽取准确度优化 + 追问策略 |
| 讲解文档 + 拓展阅读 | 2 | 提示词调优 + docx/pptx 导出 |
| 思维导图 + 练习题目 | 2 | Mermaid 渲染 + 分层出题质量 |
| 视频/动画生成 | 2 | 多模态方案落地 |
| 学习路径规划 | 2 | 路径合理性 + 资源绑定 |
| 前端界面 | 3 | 对话页 / 画像可视化 / 资源展示 / 路径页 |
| 测试与文档 | 1-2 | 测试覆盖 + 答辩材料 |
| 部署 | 1-2 | 服务器部署 + 演示环境 |

### 每人认领时的注意事项

1. **一人一个模块**，避免两人改同一个文件（冲突很痛）
2. 公共文件（`schemas.py`、`config.py`、`client.ts`）**改动前在群里说**
3. 加分项（需求 4、5）建议给**进度快的同学**，不要一开始就铺太开
4. 每周末合并一次到 `main`，保证随时有可运行版本

## 七、答辩准备要点

这套脚手架刻意留下了几个**适合答辩讲的设计点**：

1. **多智能体协作不是噱头** —— 讲清"黑板模式 + 并行调度 + 失败隔离"，
   并当场展示 `agent_log` 里各智能体的协作记录
2. **画像真的在起作用** —— 展示同一主题、不同画像生成出不同资源
3. **降级策略** —— 讲清视频资源在无 API 时如何降级为脚本+动画，
   体现工程思维（而不是留个坑）
4. **可见的架构** —— `/docs` 的接口文档、`/api/env-check` 的自检
5. **测试覆盖需求指标** —— `pytest` 里直接断言"≥5 类资源""≥6 维度"

> 💡 建议做一个**演示脚本**：从空白画像开始 → 3 轮对话 → 生成 5 类资源 →
> 生成学习路径 → 展示协作日志。全程 5 分钟内，不要现场调 bug。

## 八、遇到分歧怎么办

1. 先看本文档和 `README.md` 有没有规定
2. 没有的话，在群里**说清利弊**，不要只说"我觉得"
3. 24 小时内没共识，找技术负责人拍板
4. 拍板结果**写进这份文档**，避免下次再吵

> 最怕的不是选错，是**各做各的**。
